# 前后端容器组合测试

本文只覆盖 QuantMind 前端和后端代码的构建、运行组合。PostgreSQL、Redis
及 RSSHub、Huntly、QwenPaw 等第三方服务沿用已拉取的镜像，不会因为下列
命令而重新构建。

## 共用准备

根目录 `.env` 保存 Compose 基础设施配置；浏览器版前端端口在这里配置：

```dotenv
WEB_HOST_PORT=3080
```

`backend/.env` 保存应用配置。数据库与 Redis 主机名不要写入这两个文件：
本地 Python 会自动使用 `127.0.0.1`，后端容器会自动使用 `db` 和 `redis`。

先保证基础设施镜像已运行：

```bash
docker compose up -d db redis
```

若本次测试涉及资讯或 QuantBot，再按需启动预构建的第三方镜像；这里没有
`--build`：

```bash
docker compose up -d rsshub huntly qwenpaw
```

## 场景 1：前端和后端均由 Docker 构建并运行

这是部署及镜像验证场景。`quantmind` 和 `web` 是唯一会构建代码镜像的服务，
Celery Worker/Beat 复用 `quantmind-oss` 后端镜像；前端浏览器入口为
`http://服务器地址:3080`，API 对宿主机公开在 `:8000`。

```bash
docker compose up -d --build --force-recreate \
  quantmind celery-worker celery-beat web
docker compose ps quantmind celery-worker celery-beat web
```

前端构建不写入固定 API 域名，而是请求同源 `/api` 和 `/ws`；Web 容器的
Nginx 默认将这些请求代理到 Docker 网络中的 `quantmind:8000`。

`quantmind`、Celery 镜像不再挂载宿主机的 `backend/`、`config/`、`scripts/`
或策略模板目录，因此容器执行的是 Dockerfile 构建进镜像的版本，而不是本地
源码的覆盖版本。

## 场景 2：前端容器化，后端由本地 Python 运行

先停止可能占用 8000 端口的后端容器，并启动本地后端：

```bash
docker compose stop quantmind celery-worker celery-beat
conda run --no-capture-output -n quantmind python -m backend.main_oss
```

`main_oss` 会同时初始化 API、Engine、Trade、Stream，首次启动可能需要数十秒。
**在 `/health` 返回成功前不要启动浏览器前端或判断启动失败**：

```bash
until curl -fsS http://127.0.0.1:8000/health; do sleep 2; done
```

在另一个终端构建并启动 Web 容器。`WEB_API_UPSTREAM` 只对这一次 Compose
调用生效，不会写入 `.env`，也不会影响随后完整容器化的默认行为：

```bash
WEB_API_UPSTREAM=host.docker.internal:8000 \
  docker compose up -d --build --force-recreate --no-deps web
```

浏览器仍访问 `http://服务器地址:3080`。Web 容器将 `/api`、`/ws` 反向代理到
宿主机的本地后端 `:8000`。Compose 为 Linux 配置了
`host.docker.internal:host-gateway`，Docker Desktop 也兼容此名称。

`--no-deps` 必不可少：它阻止 Web 服务因 `depends_on: quantmind` 自动启动另一个
后端容器。测试完成后，恢复场景 1 只需重新执行场景 1 的命令。

## 场景 3：后端容器化，前端使用 Vite 开发服务器

只构建并运行后端代码镜像：

```bash
docker compose up -d --build --force-recreate \
  quantmind celery-worker celery-beat
```

然后在宿主机启动前端开发服务器：

```bash
# 使用后端实际可访问的地址；局域网服务器示例：
export VITE_API_URL=http://192.168.1.111:8000
npm run dev:web
```

Vite 默认监听 `3000`，因此浏览器访问 `http://服务器地址:3000`。开发服务器
会把 `/api` 与 `/ws` 代理到 `VITE_API_URL` 指定的后端。后端与前端运行在同一台
宿主机时，也可明确设为 `http://127.0.0.1:8000`；Docker 已将 `quantmind` 的 API
端口发布到该地址。此场景无需构建或启动 `web` 服务。

必须在启动 Vite **之前**设置 `VITE_API_URL`；它会覆盖 Vite 代理目标。若设置成
不存在的域名或错误端口，终端会出现 `getaddrinfo ENOTFOUND` 或
`ECONNREFUSED`，登录与所有 API 请求都会失败。

当前项目的 `dashboard:dev` 和 `dev:web` 都会调用 Electron 工作区的 `dev` 脚本。
在只测试浏览器页面的 Linux 环境中，即使 Electron 因缺少系统库（例如
`libasound.so.2`）退出，Vite 开发服务器仍可继续提供网页；以终端显示的 Vite
地址为准。

如果此前运行过浏览器版 Web 容器，可选择停止它以避免混淆两个前端入口：

```bash
docker compose stop web
```

它现在使用 3080，不会与 Vite 的 3000 端口冲突。

## 验证与排查

```bash
curl -fsS http://127.0.0.1:8000/health
curl -fsS http://127.0.0.1:3080/health
docker compose ps
```

场景 2 若 Web 返回 `502`，首先确认本地后端进程确实监听 `8000`，再确认启动
Web 时使用了 `WEB_API_UPSTREAM=host.docker.internal:8000` 和 `--no-deps`。
不要把 `WEB_API_UPSTREAM` 持久写成宿主机地址；默认值 `quantmind:8000` 才是
场景 1 的容器内地址。
